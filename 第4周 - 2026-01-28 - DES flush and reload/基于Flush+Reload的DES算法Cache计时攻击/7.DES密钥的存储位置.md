# 密钥的存储位置详解

在Flush+Reload攻击中，**密钥不存储在共享库中**，而是**由调用者传入**。让我详细解释：

## 一、正确设计：密钥作为函数参数

查看你的DES函数声明：
```c
void des_encrypt(const uint64_t plaintext, const uint64_t key, uint64_t *result);
//                                              ↑
//                                    密钥作为参数传入
```

**这是正确的设计**，因为：

### 1. **加密函数应该是通用的**
共享库应该提供通用的加密功能，接受任意密钥：
```c
// 共享库不知道密钥是什么
// 它只是根据传入的密钥执行加密算法
```

### 2. **攻击场景**
在实际攻击中：
- 目标进程有自己的密钥（攻击者不知道）
- 目标进程调用`des_encrypt(plaintext, 目标密钥, &ciphertext)`
- 共享库只是执行算法的"工具"，不保存密钥

### 3. **共享库的职责**
共享库的职责是：
- 提供DES算法实现
- 提供S-box等数据结构
- **不**存储任何特定的密钥

## 二、总结

**在Flush+Reload攻击中：**

| 组件             | 是否存储密钥 | 说明                             |
| ---------------- | ------------ | -------------------------------- |
| **共享库 (.so)** | ❌ **不存储** | 只提供算法实现，密钥作为参数传入 |
| **目标进程**     | ✓ **存储**   | 有自己的私有密钥（攻击目标）     |
| **间谍进程**     | ❌ **不知道** | 试图通过侧信道恢复密钥           |

**关键点：**
1. 共享库是**算法容器**，不是**密钥容器**
2. 密钥是目标进程的**私有数据**
3. 攻击者通过**侧信道分析**间接恢复密钥
4. 共享库的S-box是**共享的**，但密钥是**私有的**

你的代码设计是正确的：`des_encrypt`函数接受密钥作为参数，共享库本身不存储特定密钥。这正是Flush+Reload攻击能够工作的前提——攻击者不知道密钥，但可以通过监控共享的S-box访问来推断密钥。
