## DES Flush+Reload Attack 项目技术面试题

---

### 一、缓存侧信道攻击原理

**Q1: 请解释 Flush+Reload 攻击的基本原理，为什么它能泄露密钥信息？**

**参考答案:**

```
Flush+Reload 利用 CPU 缓存的时间差异：
1. Flush: 攻击者将目标内存行从缓存中驱逐（clflush指令）
2. Trigger: 触发受害者执行加密操作
3. Reload: 测量重新加载目标内存行的时间

原理：
- 如果受害者访问了该内存行 → 数据在缓存中 → Reload 快（命中）
- 如果受害者未访问 → 数据在内存中 → Reload 慢（未命中）

在 DES 中，S-box 查找表是共享的常量数据。通过观察受害者访问了哪些 S-box 条目，可以推断出密钥信息。
```

**追问 Q1.1: 为什么需要 Flush？直接测量不行吗？**

```
直接测量的问题：
1. 无法确定初始缓存状态
2. 可能受到其他进程干扰
3. 无法区分"命中"和"未命中"

Flush 的作用：
- 建立已知的初始状态（缓存为空）
- 确保测量的准确性
- 使攻击可重复
```

### 二、时序测量精度

**Q2: 代码中使用 rdtsc 指令测量时间，请解释其原理和精度。为什么选择它而不是 gettimeofday？**

**参考答案:**
```
rdtsc (Read Time-Stamp Counter):
- 读取 CPU 内部的时钟周期计数器
- 精度：单个 CPU 周期（约 0.3-1ns）
- 开销：约 25-100 个周期

gettimeofday:
- 系统调用，精度微秒级（1000ns）
- 需要陷入内核，开销大
- 受系统调度影响

选择 rdtsc 的原因：
1. 精度高：可以区分缓存命中（~50 cycles）和未命中（~200 cycles）
2. 开销低：不影响被测量的代码
3. 用户空间：不需要系统调用
```

**追问 Q2.1: rdtsc 有什么局限性？如何克服？**

```
局限性：
1. CPU 频率变化：现代 CPU 动态调频
2. 多核问题：不同核心的 TSC 可能不同步
3. 指令乱序：可能被 CPU 乱序执行

解决方案：
1. 使用 rdtscp（带序列化的 rdtsc）
2. 添加内存屏障（mfence）防止乱序
3. 绑定到特定 CPU 核心
4. 多次测量取平均
```

### 三、缓解措施设计

**Q3: 你的缓解措施使用了"钩子机制"，请解释为什么这比传统的"一次性应用"更有效？**

**参考答案:**

```
传统方式的问题：
mitigation_apply();   // 只在开始执行一次
attack();             // 攻击过程中无保护
mitigation_remove();  // 结束移除

问题：攻击过程可能持续数秒，缓解措施只在开始时生效

钩子机制的优势：
for (每次加密) {
    mitigation_hook_pre_encrypt();  // 每次加密前执行
    encrypt();                      
    mitigation_hook_post_encrypt(); // 每次加密后执行
}

优势：
1. 持续保护：缓解措施贯穿整个攻击过程
2. 精准定位：在最关键的操作前后插入
3. 动态调整：可以根据攻击强度调整缓解策略
4. 组合灵活：易于组合多种缓解措施
```

**追问 Q3.1: 你的实验中，为什么 Noise Injection 和 Access Obfuscation 有效，而 Cache Flush 效果有限？**

```
Noise Injection 有效的原因：
- 随机延迟破坏了攻击者的时间同步
- Flush+Reload 依赖精确的时序测量
- 噪声使攻击者难以建立稳定的时序关联

Access Obfuscation 有效的原因：
- 随机延迟混淆了访问时序
- 攻击者无法确定真实的访问模式

Cache Flush 效果有限的原因：
1. 开销太大：每次冲洗 512 个缓存行
2. 频率不够：每 10 次加密冲洗一次，中间有窗口期
3. 可能帮助攻击：冲洗后缓存状态更"干净"，反而有利于测量

改进方向：
- 增加冲洗频率（但会进一步降低性能）
- 使用硬件缓存分区（Intel CAT）
```

### 四、实验设计

**Q4: 你为什么选择 25 轮迭代？如何确定这个样本量足够？**

**参考答案:**
```
样本量演进：
- 3 轮：效果相同（33.3%），可能是随机波动
- 10 轮：效果开始分化，但仍有较大方差
- 25 轮：效果分布稳定，统计显著

确定样本量的方法：
1. 观察收敛性：当结果不再大幅变化时
2. 置信区间：计算 95% 置信区间
3. 效应量：根据预期效应量计算所需样本

25 轮的优势：
- 可以检测 4% 的效应差异（80% 功效）
- 结果稳定，可重复
- 计算成本可接受
```

**追问 Q4.1: 你的实验中出现了"假阳性"（某些缓解措施实际上无效但显示有效），如何排除？**

```
假阳性的原因：
1. 攻击本身不稳定（基线成功率 84%，不是 100%）
2. 系统噪声（后台进程、中断等）
3. 随机波动（小样本时尤其明显）

排除方法：
1. 增加样本量（从 3 轮增加到 25 轮）
2. 多次重复实验，观察一致性
3. 对照实验：测试"安慰剂"缓解措施（如空操作）
4. 统计分析：计算 p 值，确保结果显著
5. 理论验证：缓解措施的原理是否符合预期

在我们的实验中：
- CPU Pinning 最初显示 33.3% 效果，但 25 轮后显示 0%（甚至负效果）
- 这说明小样本时的"有效"可能是假阳性
```

### 五、系统安全

**Q5: 你的攻击需要 root 权限（sudo），为什么？实际攻击中攻击者如何获得这些权限？**

**参考答案:**
```
需要 root 权限的操作：
1. clflush 指令：用户空间可用，但共享内存需要特权
2. 大页内存：通常需要特权分配
3. CPU 亲和性：sched_setaffinity 可能需要特权
4. 内核 PMU：性能监控单元访问

实际攻击场景：
1. 云环境：攻击者和受害者在同一物理机（不同 VM）
   - 共享 LLC 缓存
   - 不需要 root，只需要用户空间代码
   
2. 浏览器攻击：JavaScript 实现 Flush+Reload
   - 利用 WebAssembly 的精确计时
   - 不需要任何特权

3. 侧信道不需要特权：
   - 缓存是共享资源
   - 时间测量可以在用户空间完成
   - 只需要与受害者共享内存（如共享库）
```

**追问 Q5.1: 如何防御这种攻击？软件和硬件层面分别有什么方案？**

```
软件层面：
1. 常量时间代码：消除密钥相关的分支和内存访问
2. 缓存预加载：在加密前加载所有可能访问的数据
3. 噪声注入：添加随机延迟（如我们的缓解措施）
4. 进程隔离：将敏感操作隔离到独立进程/核心

硬件层面：
1. Intel CAT (Cache Allocation Technology)：缓存分区
2. AMD SEV (Secure Encrypted Virtualization)：内存加密
3. 禁用超线程：消除 SMT 侧信道
4. 专用加密硬件：如 Intel AES-NI，不经过缓存

我们的实验结论：
- 软件缓解最多 33.3% 效果
- 硬件缓解（如 CAT）可能提供更强保护
- 组合使用多种措施效果最佳
```

### 六、代码优化

**Q6: 代码中使用了 `asm volatile ("mfence" ::: "memory")`，请解释作用。可以省略吗？**

**参考答案:**

```
mfence 的作用：
1. 内存屏障：确保之前的内存操作完成
2. 防止乱序：CPU 不会将 mfence 后的指令提前
3. 序列化：确保 rdtsc 测量的准确性

代码中的使用场景：
flush_cache();           // 1. 执行 clflush
asm volatile ("mfence"); // 2. 确保 flush 完成
mitigation_hook();       // 3. 缓解措施
encrypt();               // 4. 加密

可以省略吗？
- 测试环境：可以，但测量可能不准确
- 生产环境：不可以，必须确保时序正确

替代方案：
- lfence：更轻量，只防止 load 乱序
- sfence：只防止 store 乱序
- rdtscp：内置序列化的 rdtsc
```

### 七、项目扩展

**Q7: 如果要将这个攻击扩展到 AES-256，需要做哪些修改？AES 的 T-table 实现与 DES 的 S-box 有何不同？**

**参考答案:**
```
修改内容：
1. 替换目标库：从 libdes.so 改为 OpenSSL 或类似库
2. 修改 T-table 地址计算：AES 有 4 个 T-table（T0-T3），每个 256 个条目
3. 调整阈值：AES 的访问模式不同，需要重新校准
4. 第一轮攻击：AES 有 10-14 轮，需要针对第一轮设计攻击

DES S-box vs AES T-table：
DES:
- 8 个 S-box，每个 64 个条目
- 每个 S-box 独立查找
- 密钥直接决定访问哪个条目

AES:
- 4 个 T-table（T0, T1, T2, T3），每个 256 个条目
- 每轮使用所有 4 个 T-table
- 字节代换 + 列混淆合并在一个表查找中
- 泄露的信息量更大，但分析更复杂

攻击难度：
- AES T-table 实现：相对容易，已有成熟攻击
- AES-NI 指令集：硬件实现，不经过缓存，无法攻击
```

### 八、工程实践

**Q8: 项目中使用了共享内存（g_sboxes）来模拟攻击，实际攻击中如何确定与受害者共享内存？**

**参考答案:**

```
实际攻击中的共享内存来源：
1. 共享库（.so 文件）：
   - 如 libc.so、libcrypto.so
   - 只读数据段在进程间共享
   - 攻击：找到库在内存中的位置，flush 其中的数据

2. 大页内存（Huge Pages）：
   - 操作系统级别的共享
   - 攻击：分配大页，与受害者共享物理页

3. 内存去重（KSM）：
   - Linux 内核合并相同内容的页
   - 攻击：创建与受害者相同的页，等待合并

4. 云服务：
   - 同一物理机上的不同 VM
   - 共享 LLC 缓存（不是内存，但攻击原理类似）

代码中的模拟：
- 我们使用 g_sboxes 数组模拟共享的 S-box
- 实际攻击中，需要找到受害者使用的共享内存区域
- 技术：/proc/[pid]/maps 查看内存映射
```
