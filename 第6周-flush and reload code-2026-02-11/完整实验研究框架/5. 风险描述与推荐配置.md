## 二、风险评估

### 2.1 高危风险

#### R1: 共享LLC缓存侧信道攻击

**风险等级**: 🔴 **高危**

**描述**:

- 虽然超线程已禁用，但2个vCPU共享L3缓存
- Flush+Reload攻击可以跨核心工作
- 攻击成功率: 84% (25轮实验)

**攻击场景**:
```
攻击者(VM1) ←→ 共享L3 ←→ 受害者(VM2)
     ↓              ↓
  Flush+Reload   缓存状态变化
     ↓              ↓
  推断密钥信息 ← 时序差异
```

**影响**:
- DES密钥泄露
- AES密钥泄露（如果使用T-table实现）
- RSA私钥泄露（如果实现不当）

**现有缓解**: 
- 无硬件级缓存分区
- 软件缓解效果有限（33.3%）

---

#### R2: 虚拟化环境逃逸风险

**风险等级**: 🔴 **高危**

**描述**:
- VMware虚拟化存在已知侧信道漏洞
- L1 Terminal Fault (L1TF) 风险
- Foreshadow攻击变种

**攻击路径**:
1. 攻击者通过侧信道获取敏感信息
2. 结合其他漏洞实现VM逃逸
3. 影响宿主机和其他VM

**现有防护**:
- L1D Flush已启用
- 但性能开销大

---

#### R3: 推测执行攻击残留风险

**风险等级**: 🟠 **中高危**

**描述**:
- Spectre v1/v2/v4 缓解措施已启用
- 但新型变种不断出现
- 微架构数据采样(MDS)风险

**已启用缓解**:

```
IBRS  - 限制间接分支推测
IBPB  - 分支预测屏障
STIBP - 单线程分支预测器隔离
SSBD  - 禁用推测存储绕过
```

**残留风险**:

- 推测执行的根本问题未解决
- 新型攻击变种可能绕过现有缓解

---

### 2.2 中危风险

#### R4: 高精度时序攻击

**风险等级**: 🟡 **中危**

**描述**:
- rdtsc/rdtscp指令可精确测量时间
- 精度达单个CPU周期(~0.4ns)
- 无法禁用（用户空间可用）

**攻击利用**:
```c
// 攻击者代码
uint64_t t1 = rdtsc();
sensitive_operation();
uint64_t t2 = rdtsc();
// t2-t1 泄露信息
```

**缓解难度**: 高（需要修改硬件或禁用高精度计时）

---

#### R5: 内存去重(KSM)风险

**风险等级**: 🟡 **中危**

**描述**:

- Linux KSM可能合并相同内存页
- 创建跨VM的共享内存
- 为Flush+Reload攻击创造条件

**检查命令**:
```bash
# 检查KSM是否启用
cat /sys/kernel/mm/ksm/run
# 1 = 启用, 0 = 禁用
```

---

### 2.3 低危风险

#### R6: 软件缓解措施绕过

**风险等级**: 🟢 **低危**

**描述**:

- 我们的软件缓解措施可被针对性绕过
- 例如：Noise Injection的对称噪声可被平均掉
- 但攻击复杂度显著提高

## 三、推荐配置

### 3.1 硬件级缓解（推荐）

#### H1: 启用Intel CAT (Cache Allocation Technology)

**配置方法**:

```bash
# 检查CAT支持
cat /proc/cpuinfo | grep cat

# 使用pqos工具配置
sudo apt install intel-cmt-cat

# 分配缓存分区
sudo pqos -e "llc:1=0x0001;llc:2=0x0002"
sudo pqos -a "pid:1234=1;pid:5678=2"
```

**效果**: 完全隔离缓存，阻止跨VM攻击

---

#### H2: 禁用超线程（已实施）

**验证状态**:
```bash
# 当前状态
lscpu | grep "Thread(s) per core"
# 输出: 1 （已禁用）
```

**如需在BIOS中禁用**:
1. 重启进入BIOS/UEFI
2. 找到 "Hyper-Threading" 选项
3. 设置为 "Disabled"
4. 保存并退出

---

#### H3: 使用AES-NI指令集

**配置方法**:
```c
// 代码中使用AES-NI，不经过缓存
#include <immintrin.h>

// 硬件AES加密，不暴露内存访问模式
__m128i _mm_aesenc_si128(__m128i data, __m128i key);
```

**验证支持**:
```bash
grep aes /proc/cpuinfo | head -1
# 输出包含 "aes" 表示支持
```

---

### 3.2 内核级缓解

#### K1: 禁用KSM（内存去重）

```bash
# 临时禁用
echo 0 | sudo tee /sys/kernel/mm/ksm/run

# 永久禁用
echo "KSM_ENABLED=0" | sudo tee /etc/default/qemu-kvm

# 验证
cat /sys/kernel/mm/ksm/run
# 输出: 0
```

**效果**: 防止跨VM内存共享

---

#### K2: 启用内核页表隔离(KPTI)

**检查状态**:
```bash
grep kpti /proc/cmdline
# 应包含 "kpti=on" 或 "pti=on"
```

**如未启用，修改GRUB**:

```bash
# 编辑GRUB配置
sudo nano /etc/default/grub
# 修改: GRUB_CMDLINE_LINUX_DEFAULT="quiet kpti=on"

sudo update-grub
sudo reboot
```

---

#### K3: 限制rdtsc精度

**方法**: 使用内核模块或虚拟化层限制

**QEMU/KVM配置**:
```bash
# 在VM配置中添加
-cpu host,-rdtscp
```

**效果**: 降低时序攻击精度

---

### 3.3 软件级缓解

#### S1: 常量时间代码实现

**原则**:

```c
// ❌ 不安全：密钥相关的分支
if (key_bit) {
    do_A();
} else {
    do_B();
}

// ✅ 安全：常量时间实现
do_A();
do_B();
result = key_bit ? result_A : result_B;
```

**工具**: 使用Valgrind的ctgrind检测非常量时间代码

---

#### S2: 缓存预加载（Cache Prefetching）

```c
// 在加密前预加载所有可能访问的数据
for (int i = 0; i < 256; i++) {
    _mm_prefetch(&T_table[i], _MM_HINT_T0);
}

// 内存屏障
asm volatile ("mfence" ::: "memory");

// 执行加密
encrypt();
```

**效果**: 消除缓存访问差异

---

#### S3: 噪声注入（已测试）

**推荐配置**:

```c
// 随机延迟范围: 100-500 cycles
volatile int delay = rand() % 400 + 100;
for (volatile int i = 0; i < delay; i++) {
    asm volatile ("nop");
}
```

**效果**: 33.3%缓解效果

## 五、应急响应

### 发现攻击迹象

1. **立即隔离**: 将受影响VM迁移到独立物理机
2. **收集证据**: 保存内存转储和日志
3. **更换密钥**: 立即轮换所有加密密钥
4. **安全审计**: 检查是否有数据泄露

### 长期改进

1. 升级到支持TDX/SEV的硬件
2. 使用专用加密硬件(HSM)
3. 实施零信任架构
4. 定期安全评估

## 六、总结

| 风险等级 | 数量 | 主要缓解措施 |
|---------|------|------------|
| 🔴 高危 | 2 | 硬件缓存分区、VM隔离 |
| 🟠 中高危 | 1 | 推测执行缓解 |
| 🟡 中危 | 2 | 禁用KSM、限制时序 |
| 🟢 低危 | 1 | 软件缓解 |

**关键建议**:
1. **短期**: 禁用KSM，启用软件缓解
2. **中期**: 部署Intel CAT缓存分区
3. **长期**: 升级到支持TDX/SEV的硬件平台
