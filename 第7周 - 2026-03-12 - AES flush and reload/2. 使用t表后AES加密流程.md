## 1. 状态初始化
将 16 字节的明文按列填充到 4×4 的状态矩阵中（行索引 r=0..3，列索引 c=0..3）：

```
state[r][c] = plaintext[4*c + r]
```

例如，第 0 列的 4 个字节是 plaintext[0], plaintext[1], plaintext[2], plaintext[3]；第 1 列是 plaintext[4], plaintext[5], plaintext[6], plaintext[7]；以此类推。

## 2. 初始轮（仅 AddRoundKey）
将状态矩阵的每一列（32 位）与第 0 个轮密钥的对应列进行异或：
```
for c in 0..3:
    col = (state[0][c] << 24) | (state[1][c] << 16) | (state[2][c] << 8) | state[3][c]
    col ^= roundKey[0][c]   // roundKey[0][c] 是第 0 轮密钥的第 c 列（32 位）
    将 col 拆回 4 个字节存回 state[0][c]...state[3][c]
```
（实际实现中常将状态直接作为 4 个 32 位字数组处理，这里为了清晰仍按字节描述）

## 3. 主循环：第 1 轮到第 9 轮
对于每一轮 round = 1 到 9：
- 使用当前状态（字节矩阵）计算新状态，并将结果存入新矩阵 new_state。
- 对每一列 c（0..3）：
  1. 从当前状态中取出四个字节，**注意索引经过了 ShiftRows 的预偏移**：
     ```
     a0 = state[0][c]                // 第0行，列c
     a1 = state[1][(c+1) % 4]        // 第1行，列(c+1)
     a2 = state[2][(c+2) % 4]        // 第2行，列(c+2)
     a3 = state[3][(c+3) % 4]        // 第3行，列(c+3)
     ```
  2. 用这四个字节分别查 T 表，得到四个 32 位字，然后异或在一起，再异或上当前轮的轮密钥的第 c 列：
     ```
     word = T0[a0] ^ T1[a1] ^ T2[a2] ^ T3[a3] ^ roundKey[round][c]
     ```
     （注意：T0[a0] 的 4 个字节已经按顺序对应新列的第 0 行、第 1 行、第 2 行、第 3 行）
  3. 将 word 拆成 4 个字节，存入 new_state 的第 c 列：
     ```
     new_state[0][c] = (word >> 24) & 0xFF
     new_state[1][c] = (word >> 16) & 0xFF
     new_state[2][c] = (word >> 8) & 0xFF
     new_state[3][c] = word & 0xFF
     ```
- 将 new_state 复制回 state（或交换指针），准备下一轮。

## 4. 最终轮：第 10 轮
最后一轮没有 MixColumns，所以不能直接使用 T0~T3（因为它们包含了 MixColumns 的乘法）。通常有两种处理方式：
- **方式 A**：单独实现 SubBytes 和 ShiftRows，然后 AddRoundKey。
  - 对每个字节进行 S 盒替换：`state[r][c] = S盒[state[r][c]]`。
  - 对状态矩阵进行行移位（与加密相同）：
    - 第 0 行不变
    - 第 1 行循环左移 1 字节
    - 第 2 行循环左移 2 字节
    - 第 3 行循环左移 3 字节
  - 最后将状态与第 10 轮密钥异或（逐字节或按列异或）。
- **方式 B**：使用专门为最后一轮准备的表（常称为 Te4 或 T4），该表仅合并了 SubBytes 和 ShiftRows，没有 MixColumns 系数。每个表项也是 32 位字，但四个字节都是同一个 S 盒输出的复制（或者经过适当排列）。这样最后一轮也可以按列查表，但公式变为：
  ```
  word = T4[a0] ^ T4[a1] ^ T4[a2] ^ T4[a3] ^ roundKey[10][c]
  ```
  但需要注意，T4 表需要配合正确的字节偏移（因为 ShiftRows 已经体现在索引 a0..a3 的取法中了）。实际上很多优化实现会使用四个不同的最后一轮表（类似 T0~T3 但系数全为 01），但原理相同。

这里我们采用**方式 A**描述，因为它更直观且不依赖额外表。

### 最终轮具体步骤：
1. **SubBytes**：对 state 中的每个字节进行 S 盒替换。
2. **ShiftRows**：对 state 矩阵进行循环左移位（与前面相同）。
3. **AddRoundKey**：将 state 与第 10 轮密钥（roundKey[10]）异或（按列或逐字节）。

## 5. 输出密文
将最终 state 按列读出 16 字节，得到密文：
```
ciphertext[4*c + r] = state[r][c]
```

## 总结流程图
1. 明文 → 初始状态
2. 初始轮：状态 ^= 轮密钥0
3. for round = 1..9:
   - for c in 0..3:
       a0 = state[0][c]
       a1 = state[1][(c+1)%4]
       a2 = state[2][(c+2)%4]
       a3 = state[3][(c+3)%4]
       new_col = T0[a0] ^ T1[a1] ^ T2[a2] ^ T3[a3] ^ roundKey[round][c]
       将 new_col 存入新状态的列 c
   - 更新状态
4. 最终轮：SubBytes → ShiftRows → AddRoundKey(轮密钥10)
5. 状态 → 密文

这样，我们就完整描述了使用 T 表的 AES-128 加密流程。T 表的引入使得每轮的计算从复杂的 MixColumns 乘法变成了 4 次查表和 4 次异或（加上取索引的偏移），极大提升了软件执行效率。

## T表的使用：

在带 T 表的 AES 实现中，`Te1` 表针对的是状态矩阵的**第 1 行**（Row 1），而不是第 1 列。

### 📊 T 表与状态矩阵行的对应关系
根据 T-BOX 架构的权威解释，状态矩阵的每一行会使用一个特定的 T 表来进行查表运算：

*   状态矩阵的**第 0 行**使用 `Te0` 表
*   状态矩阵的**第 1 行**使用 `Te1` 表
*   状态矩阵的**第 2 行**使用 `Te2` 表
*   状态矩阵的**第 3 行**使用 `Te3` 表

这个对应关系直接体现在查表计算的公式中。在计算新的一列（如 `t0`）时，会用 `Te1` 去查 `(s1 >> 16) & 0xff` 这个值。这里 `s1` 代表状态矩阵的第1列，其**次高字节**正好是状态矩阵中**第1行第1列**的字节。

### 💡 为什么在攻击中关注的是“行”？
在 Flush+Reload 攻击的上下文中，我们关注的正是这种**表与行的对应关系**。当一个 T 表的缓存行未被访问时，它意味着在加密过程中，该表没有被用于计算。

*   **攻击逻辑**：如果 `Te1` 表的某个缓存行（例如对应输入值 0-15）没有被访问，那么在这次加密中，所有需要使用 `Te1` 表的地方——也就是状态矩阵的**第 1 行**的四个字节——所对应的输入字节，都不可能落在 0-15 的范围内。
*   **影响范围**：因此，这个缓存未命中事件会用于排除**第 1 行**所有四个字节（即密钥字节位置 4, 5, 6, 7）的候选值。

### 📝 关键概念澄清
可能造成混淆的点在于：T 表的**输入**是一个字节的值（0-255），这个值在查表时作为索引。在 T 表实现中，这个输入值来源于状态矩阵的某个字节，而这个字节在状态矩阵中的**行位置**，就决定了它会去查哪个 T 表。因此，我们可以理解为，T 表是**按行分工**的，而不是按列。

## 注意：最终轮的T表与S表的关系

在 AES 的 T 表实现中，**最终轮使用的 T 表和中间轮是同一组表（Te0～Te3）**，但**使用方法不同**，因为最终轮不包含 MixColumns 操作。

### 1. 为什么中间轮可以用 T 表完成 MixColumns？
T 表的设计初衷是加速**标准轮**（SubBytes + ShiftRows + MixColumns）。每个 T 表项是一个 32 位字，其四个字节分别存储了 **S 盒输出乘以 MixColumns 矩阵中不同系数**的结果。例如：
```
Te0[x] = (2·S[x]) << 24 | (S[x]) << 16 | (S[x]) << 8 | (3·S[x])
```
当中间轮计算新的一列时，我们通过异或四个 T 表的输出，相当于完成了：
- 四个输入字节分别经过 S 盒；
- 将 S 盒结果分别乘以 MixColumns 矩阵中对应行的系数；
- 然后将这些乘积按位异或，得到新列的四个字节。
这正是 MixColumns 的数学本质。

### 2. 为什么最终轮不能直接这样用？
最终轮**没有 MixColumns**，只做 SubBytes、ShiftRows 和 AddRoundKey。如果仍然用四个 T 表的输出异或，就会**错误地多执行一次 MixColumns**，导致加密结果错误。

### 3. 最终轮如何利用 T 表？
虽然最终轮不 MixColumns，但我们仍然可以从 T 表中**提取出单纯的 S 盒结果**，因为每个 T 表项的四个字节中，**有一些字节本身就是 S[x]**（或者可以通过简单变换得到 S[x]）。例如：
- Te0[x] 的**第二个字节**（从高位算起）就是 S[x]。
- Te1[x] 的**第三个字节**是 S[x]。
- Te2[x] 的**最高字节**是 S[x]。
- Te3[x] 的**最低字节**是 S[x]（注意 Te3[x] 构造为 (S[x], S[x], 3·S[x], 2·S[x])，最低字节是 2·S[x]？等一下需要核对）。
实际上，OpenSSL 等实现中，最终轮是这样利用 T 表的：
```
t0 = (Te2[(s0 >> 24) & 0xff] & 0xff000000) |
     (Te3[(s1 >> 16) & 0xff] & 0x00ff0000) |
     (Te0[(s2 >> 8) & 0xff] & 0x0000ff00) |
     (Te1[s3 & 0xff] & 0x000000ff);
```
这里：
- Te2 的高字节是 S[·]（因为 Te2 = (S, 3·S, 2·S, S)？标准 Te2 = (S, 3·S, 2·S, S)，所以高字节是 S）。
- Te3 的次高字节是 S（Te3 = (S, S, 3·S, 2·S)）。
- Te0 的次低字节是 S（Te0 = (2·S, S, S, 3·S)）。
- Te1 的最低字节是 S（Te1 = (3·S, 2·S, S, S)？标准 Te1 = (3·S, 2·S, S, S)，最低字节是 S）。
通过掩码提取这些字节，再拼成一个新的 32 位字，就相当于完成了 **SubBytes + ShiftRows**，然后异或轮密钥即可得到密文。

### 4. 总结
- **T 表是同一组表**，但最终轮使用时**只取其中代表 S 盒结果的字节**，而不是将四个表输出全部异或。
- 因此，最终轮并没有“包含列混淆”，而是通过巧妙的字节提取，仅利用了 T 表中的 S 盒部分。
- 在攻击中，监控 T 表的缓存行时，**最终轮的访问模式仍然与 T 表分工一致**（Te0 影响输出第 0 行，等等），所以攻击算法中的映射关系依然成立。
