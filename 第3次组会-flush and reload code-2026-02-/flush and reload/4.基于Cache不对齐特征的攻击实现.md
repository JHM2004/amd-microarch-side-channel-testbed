## 遇到的问题：

缓存是按缓存行（通常64字节）组织的，而每个S-box正好是64字节。当访问S-box中的任何表项时，整个S-box都会被加载到缓存中，导致无法区分具体访问的是哪个表项

## 解决方案：

在《基于 Flush + Ｒeload 的 DES 算法 Cache 计时攻击》论文中：

针对 DES 算法的 8 个 S 盒，根据 S 盒的结构，实

现 DES 算法的 S 盒，每个元素占 4 Byte，加载一个4 行

16 列的 S 盒需要256 Byte。在 Intel i7-4720HQ 处理器

中，每个 Cache 行大小为 64 Byte，clflush 指令刷新大

小为 64 Byte。如果 S 盒查找表在 Cache 中是对齐分

布，则一个 S 盒需要 4 个 Cache 行存储; 如果不对齐，

则一个 S 盒占用了 5 个 Cache 行。
使用 Linux 系统调用函数 mmap 映射 DES 算法加

密共享库到间谍进程 SP 中，运行加密算法进程后刷

新指定 Cache 行，因为一次会刷新64 Byte，所以如果 S

盒在 Cache 中对齐分布，使用该方法只能确定访问的

S 盒所在行。DES 算法有 8 个 S 盒，只对第一轮加密

进行攻击，使用 Flush + Ｒeload 方法进行一轮攻击，能

够确定加密时使用的 S 盒所在的 Cache 行。

DES 在算法查找 S 盒时，使用 6 个比特位来确

定查找的元素，首尾两位确定查找行，中间 4 位用来

确定列。经过一轮攻击，确定了行位置，能将 DES 算

法的密钥搜索空间从 256降到 232。

在 DES 算法实际运 算 环 境 中，S 盒 查 找 表 在

Cache 中不都是对齐分布，根据这种特征，本文提出

一种新的方法，用于准确获取查询的 S 盒元素在

Cache 行中的准确偏移位。

在第一轮攻击后，确认查询的 S 盒元素所在的

Cache 行。设偏移量为 0 的地址为 V［0］，将刷新地

址右偏移 4 × i Byte 的地址为 V［i］( 其中 i∈［0，15］

且 i 为整数) ，每次偏移量刚好是 S 盒一个元素的大

小。当发生 Cache 不对齐时，刷新的地址和S 盒查询

的地址在同一 Cache 行时，间谍进程第 2 次访问刷

新的地 址 时 会 发 生 Cache 命 中，反 之，不 在 同 一

Cache 行 时，就 会 发 生 Cache 失 效。对 算 法 攻 击

T 次，S 盒查找表在 Cache 中会发生多次不对齐，设

间谍进程发生 Cache 失效的次数为 n，如果刷新地址

不是查询使用的 S 盒元素，则有 n ＞ 0; 如果刷新的地址刚好是查询使用的 S 盒元素，则有 n = 0。

# 基于Cache不对齐特征的DES Flush+Reload攻击实现

## 一、问题分析

当前实现的主要问题：

- S盒元素使用1字节大小，无法充分利用Cache不对齐特征
- 传统Flush+Reload无法区分同一Cache行内的不同S盒元素
- 攻击成功率受限于Cache行粒度的探测精度

## 二、解决方案

采用用户提出的基于Cache不对齐特征的攻击方法：

### 1. 核心原理

- **S盒设计**：每个元素占4字节，一个S盒需要256字节
- **Cache行利用**：64字节Cache行，利用对齐/不对齐特征
- **精确探测**：通过4字节偏移量进行精确元素定位
- **密钥空间缩减**：从2^56降到2^32

### 2. 实现步骤

#### 步骤1：修改S盒实现

- 将S盒元素改为4字节大小
- 创建共享库实现DES加密
- 确保S盒在内存中可能出现不对齐分布

#### 步骤2：创建间谍进程

- 使用mmap映射DES共享库
- 实现Flush+Reload攻击逻辑
- 专注于第一轮加密攻击

#### 步骤3：两阶段攻击流程

- **第一阶段**：确定S盒元素所在的Cache行
- **第二阶段**：通过4字节偏移探测准确元素位置

#### 步骤4：Cache不对齐利用

- 利用实际环境中S盒的不对齐分布
- 通过刷新偏移地址观察Cache命中/失效
- 统计T次攻击中的Cache失效次数n
- 当n=0时确定为目标元素位置

### 3. 技术实现要点

#### 3.1 S盒结构修改

#### 3.4 攻击算法

1. **Flush阶段**：刷新指定Cache行
2. **Trigger阶段**：触发DES加密
3. **Reload阶段**：测量访问时间
